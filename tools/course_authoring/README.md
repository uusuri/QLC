# Подготовка уроков

Локальный адаптер инструментов `qlc-algorithm-lesson` и журнал последовательного
ревью. Не меняет глобальный skill, не запускает программы, не публикует материалы
и не подключается к БД. Учебные материалы остаются вне Git, здесь только инструменты.

Требуется Python 3.10+ и установленный skill. Если он находится не в стандартном
каталоге, передайте `--skill-root /path/to/qlc-algorithm-lesson` **перед** командой.

## Команды

```sh
python3 tools/course_authoring/authoring.py check-catalog
python3 tools/course_authoring/authoring.py lesson check /path/to/lesson
python3 tools/course_authoring/authoring.py course check /path/to/course
python3 tools/course_authoring/authoring.py snapshot /path/to/lesson --phase theory
python3 tools/course_authoring/authoring.py check /path/to/lesson --stage theory_reviewed
python3 tools/course_authoring/authoring.py snapshot /path/to/lesson --phase practice
python3 tools/course_authoring/authoring.py check /path/to/lesson --stage ready
python3 -m unittest discover -s tools/course_authoring -p 'test_*.py'
```

Команды `lesson` и `course` передают остальные аргументы штатным валидаторам,
подменяя **только в памяти текущего процесса** их каталог языков. В каталоге есть
CPython/PyPy 3.12, нет Python 3.11. `check-catalog` сверяет ID, Markdown-ограды и имена
файлов с фронтендом, наличие исполнителя — с `LanguageProfile.isRunnable`.
Наличие исполнителя в исходниках не означает, что образ собран или сервис запущен.

## Журнал `authoring.json`

Хранится рядом с `lesson.json`. Ниже пример **структуры**, не готовое свидетельство
ревью. Значения хешей и имён проверяющих нужно заменить фактическими; этот пример
не проходит проверку как есть.

```json
{
  "schema_version": 1,
  "lesson_id": "problem-to-solution",
  "sequence": 1,
  "level": 1,
  "stage": "draft",
  "previous_journal": null,
  "theory_files": ["lesson.json", "theory/CPP23.md", "code/CPP23/main.cpp"],
  "tasks_file": "tasks.json",
  "task_ids": ["task-one", "task-two", "task-three", "task-four"],
  "practice_files": [],
  "theory_reviews": [
    {
      "round": 1,
      "reviewer": "actual-reviewer-id",
      "status": "approved",
      "reviewed_at": "2026-10-24T12:00:00+03:00",
      "artifact_sha256": "actual-theory-snapshot-sha256",
      "checks": ["Какие конкретно части и свойства проверены"],
      "findings": [
        {"issue": "Обнаруженная проблема", "resolution": "Как исправлена и перепроверена", "status": "fixed"}
      ]
    }
  ],
  "practice_reviews": []
}
```

`lesson_id` совпадает со `slug` урока. В `theory_files` должны входить `lesson.json`,
**все** варианты теории и отдельные файлы полного кода. `practice_files` —
необязательные дополнительные материалы, например проверка примеров анимации.
Эталоны CODE, оракул, генератор, план тестов, отчёты и журналы запусков инструмент
подключает к отпечатку автоматически по записям `teacher`.

Пути в журнале относительны каталогу урока. Пути `teacher` относительны каталогу
`tasks.json`, как в исходном `course_tool`. Если общие задачи лежат уровнем выше,
передавайте `--course-root /path/to/course`. Без этого аргумента ссылки за пределы
урока запрещены. Абсолютные пути и выходящие из корня символические ссылки запрещены.

Изменение файлов теории, полного кода или метаданных меняет отпечаток теории и
практики. Изменение задачи/эталона/отчёта меняет отпечаток практики. Добавление задач
**другого** урока в общий `tasks.json` не меняет отпечаток текущего урока.

## Последовательность

1. Написать один урок и прогнать `lesson check`.
2. Получить `snapshot --phase theory`. Провести ревью корректности, предпосылок,
   границ, понятности и всех языковых версий. Записать реально проверенные пункты,
   замечания и исправления.
3. Провести второе независимое ревью: другой `reviewer`, `round: 2`.
4. Проверить `--stage theory_reviewed`. После редактирования повторить затронутые
   ревью и получить новый отпечаток; смены одного хеша без повторного чтения недостаточно.
5. Написать 4–5 задач, выполнить проверки эталонов, границ, случайных/максимальных
   данных и ошибочных решений. В каждой задаче `difficulty` — целое от 1 до 3:
   звёзды обозначают сложность **внутри** `level` урока, а не глобальную шкалу.
6. Получить `snapshot --phase practice`. Дважды независимо проверить условия,
   ответы, примеры, тесты, соответствие изученному и отсутствие готового решения в
   подсказках/ученических данных. Формат `practice_reviews` тот же, что у теории.
7. Проверить `--stage ready`, затем установить `stage: "ready"` в журнале.
   Только после этого начать следующий урок.

Ученическая теория заканчивается объяснением: упражнения, самопроверка и ответы
не вставляются между ним и отдельной вкладкой «Практика». Проверка всех
`variants.*.theory_file` отклоняет точные Markdown-заголовки «Проверьте себя»,
«Самопроверка», «Попробуйте самостоятельно», «Ответы» и «Разбор самопроверки»
(без учёта регистра и завершающего двоеточия). Поддерживаются заголовки с `#`
и подчёркиванием `===`/`---`; блоки кода с backtick/tilde-оградами и отступом
пропускаются. Упоминания в прозе, экранированные заголовки, inline-code и длинные
названия вроде «Ответы на запросы» не считаются самопроверкой. Авторский `review.md`
не проверяется: внутреннее ревью и учебное упражнение — разные вещи.

На этапе `draft` нарушения перечислены в `presentation_blockers`; на этапах
`theory_reviewed` и `ready` они блокируют проверку. Это узкая проверка заголовков,
не смысловая редактура и не автоматическая переработка текста. Материалы она
не изменяет. Особое визуальное оформление условия пока не требуется валидатором:
эксперимент с карточкой не должен навязывать неподтверждённый формат всем урокам.

В каждом этапе нужны ровно два разных раунда и два разных ID проверяющих.
`checks` не может быть пустым. `findings: []` допустим, если проблем действительно
не обнаружили; выдумывать замечания не нужно. Нерешённая проблема (`status: "open"`),
неодобренное ревью или старый хеш блокируют переход. Все даты содержат часовой пояс.
Ревью практики не может предшествовать последнему ревью теории. Уровень и номер
урока тоже входят в отпечатки: перенос задания в другой уровень требует проверки.

Начиная со второго урока задайте `sequence: 2` и:

```json
"previous_journal": {"directory": "../first-lesson", "journal": "authoring.json"}
```

Запускайте с общим `--course-root`. Проверяется непосредственно предыдущий номер,
его объявленный `stage: "ready"` и вся его цепочка вместе с актуальностью файлов.

## Что означает `ready`

Это не только два текстовых одобрения. Требуются согласованные отчёты о запусках
примеров полного кода (`verification.json`) для всех языковых вариантов и CODE-
проверки в формате исходного `course_tool`: эталоны всех языков, оракул, генератор,
граничные/случайные/максимальные данные, отклонённые ошибочные решения, хеши и журнал.
CODE-задачи обязаны иметь 3–5 разных подсказок.

Если интерпретатор/компилятор недоступен, **не** записывайте `executed`. Оставьте
`not_run` с причиной, а урок — `draft` или `theory_reviewed` до реальной проверки.
В выводе отдельно перечислены языки с записанными запусками, непроверенные языки
и языки без текущего исполнителя на платформе. Локальный запуск Rust, например,
не добавляет Rust-runner в QLC и не проверяет Docker judge.

Хеши защищают от случайного устаревания, но не доказывают честность заполненного
отчёта, реальность независимого ревью или отсутствие смысловой утечки ответа.
Это ручная ответственность проверяющих. Тестовые отчёты в `test_authoring.py`
явно синтетические; они проверяют сам валидатор, а не учебные решения.
