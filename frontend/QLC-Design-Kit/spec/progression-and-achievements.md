# Прогресс, XP и достижения QLC

Это локальная спецификация будущего интерфейса и примеры данных. Она не утверждает экономику наград и не описывает уже реализованный API. Figma, браузер, редактор кода и сайт в этом этапе не изменяются.

Используются существующие 30 SVG из `achievement-symbols/`. Новые иконки не генерируются. В `data/achievements.json` находятся 38 примеров: исходные 30 названий сохранены; восемь дополнительных примеров закрывают ревью, инциденты, XP и достижения Java. Дополнительные записи повторно используют подходящие знаки. Число определений достижений не ограничено числом иконок.

## 1. Что именно измеряется

Нельзя одной шкалой обозначать всё обучение. У каждой шкалы есть собственные числитель, знаменатель, подпись и источник данных.

| Объект | Основная метрика | Когда завершён | Чего не означает процент |
|---|---|---|---|
| Курс | Завершённые обязательные уроки / все обязательные уроки | Сервер подтвердил все обязательные результаты | Долю заработанного XP, просмотренного текста или доступных уроков |
| Модуль | Завершённые обязательные уроки модуля / все обязательные уроки модуля | Подтверждены обязательные уроки | Среднее процентов модулей другой длины |
| Урок | Подтверждённые шаги урока / обязательные шаги | Выполнен критерий завершения этого типа урока | Время, проведённое во вкладке, или просто прокрутку страницы |
| Coding task | Состояние submission; при доступных данных — пройденные тесты / все тесты | Итоговый verdict accepted | Ожидаемое время проверки или частичный зачёт курса |
| Навык | Отдельная оценка освоения по результатам практики | Уровень освоения определяется моделью навыка | Процент завершённых уроков |
| XP | XP внутри текущего уровня / XP, необходимые для следующего уровня | Достигнута серверная граница уровня | Долю от всех XP за всё время |
| Достижение | Подтверждённое значение конкретной метрики / цель определения | Сервер создал факт получения | Оценку сложности или редкости |

Текущий source считает learning progress через уникальные accepted задачи. Спецификация позволяет перейти к явным обязательным результатам разных типов уроков. При реализации это отдельная согласованная миграция данных; нельзя поменять подпись на «уроки», оставив знаменатель задач.

Если модуль содержит 2 урока, а другой — 20, курс считается из общей суммы завершённых и обязательных уроков. Среднее двух процентов модулей будет неверным. Необязательные материалы не входят в знаменатель; их наличие показано отдельно.

Изменение программы может изменить общий процент. Ответ API должен содержать `curriculumVersion` и согласованный снимок числителя/знаменателя. Добавление урока не аннулирует полученный ранее результат и XP. Для завершённого курса можно хранить «Завершён по программе версии N» и отдельно предложить новые материалы.

## 2. Согласованные примеры профиля и курса

Основной профиль во всех макетах использует один набор чисел:

- Уровень **12**.
- XP за всё время: **21 840 XP**.
- Начало уровня: **19 000 XP** за всё время.
- Следующий уровень: **22 500 XP** за всё время.
- Внутри уровня: **2 840 / 3 500 XP**.
- Осталось: **660 XP**.
- Точная доля заполнения: **81,14285714285714%**; компактная подпись **81%**.

Курс Java Backend: **12 модулей**, **43 / 60 обязательных уроков**, **1 840 XP** получено в курсе. Точная доля — **71,66666666666667%**; подпись **72%**. Это округление подписи, а не превращение 43 уроков в 43,2.

В демонстрационной структуре первые восемь модулей содержат по пять завершённых уроков. В девятом модуле Collections завершены три из пяти. Остальные три модуля не начаты: `40 + 3 = 43`, `12 × 5 = 60`. Текущий урок — HashMap; его внутренний progress **13 / 20 шагов = 65%**, но в число завершённых уроков он ещё не входит. Текущий модуль имеет **3 / 5 = 60%**.

Полные данные: `data/progression-examples.json`. Остальные achievement, reward и review-примеры — независимые состояния компонентов; их нельзя суммировать как историю этого профиля.

## 3. Непрерывный прогресс

Процент — число от 0 до 100, включая дробные значения. У Linear, XP, Course, Module, Lesson, Skill и Circular одна модель заполнения. Варианты 0 / 25 / 50 / 75 / 100 из брифа трактуются как примеры для проверки, а не как пять разрешённых состояний.

Для обычного счётчика:

```text
ratio = current / target
fill = clamp(ratio, 0, 1)
percentage = fill × 100
```

Linear меняет ширину заполнения или `scaleX` с левым origin. Circular меняет длину видимой дуги, а не число готовых сегментов. Значение 37,6 должно заполнить 37,6% геометрии даже при подписи 38%.

Состояния шкалы:

| Состояние | Пример | Представление |
|---|---|---|
| `determinate` | 37,6 / 100 | Точное заполнение и число |
| `indeterminate` | Проверка запущена, общее число тестов неизвестно | Подпись «Проверяем решение» и отдельный busy indicator |
| `unavailable` | Нет согласованных данных | «Прогресс временно недоступен», без выдуманного процента |
| `not_applicable` | В курсе пока нет обязательных уроков | «Программа готовится», без пустого обещания 100% |
| `invalid_data` | Отрицательный счётчик или границы уровня нарушены | Состояние ошибки данных, последний корректный снимок при наличии |

У цели достижения `target` должен быть положительным. При нуле деление не выполняется и достижение не считается полученным. У наполнения 0 нет минимальной цветной полоски. У 100 заполнение точно доходит до конца. Если счётчик превысил цель, геометрия ограничивается 100%, а фактическое число можно оставить, например `120 / 100`.

Для почти полного значения округление не должно ложным образом сообщать завершение. При `99,999%` и неподтверждённом завершении показывать `≥99,9%` либо точные количества. Бейдж «Завершено» приходит из состояния, не из округлённой подписи.

В TypeScript позже: переход к новому известному значению около **240 мс, ease-out**. Новое обновление продолжает движение из текущего видимого положения. При `prefers-reduced-motion: reduce` значение меняется сразу; бесконечное декоративное движение отключается. Не заставлять каждый открытый экран анимировать всё с нуля и не изображать неизвестную проверку медленным ростом от 0 до 99.

`role=progressbar` получает доступную подпись, min/max и актуальный now для известного процента. Для неизвестного процента `aria-valuenow` отсутствует. Screen reader не должен озвучивать каждый animation frame.

## 4. Масштабируемый уровень и XP

Компонент не содержит таблицу из десяти нарисованных уровней. `Level/Badge` принимает строку/число уровня: 1, 10, 100, 999, 1 000 и больше. Ширина адаптируется к тексту; узкое место использует перенос или компактное отображение, а полное значение остаётся доступным.

Серверный снимок XP содержит:

```text
level
lifetimeXp
levelStartLifetimeXp
nextLevelLifetimeXp
currentLevelXp
xpRequiredForLevel
xpRemaining
policyId / policyVersion
revision
```

Связи обязательны:

```text
currentLevelXp = lifetimeXp − levelStartLifetimeXp
xpRequiredForLevel = nextLevelLifetimeXp − levelStartLifetimeXp
xpRemaining = xpRequiredForLevel − currentLevelXp
0 ≤ currentLevelXp < xpRequiredForLevel
```

При точном попадании на границу снимок уже относится к следующему уровню с текущим XP = 0. Для отдельно показываемого Level Up перехода можно кратко показать предыдущее заполнение 100%, затем новый уровень. Одновременно хранить старый уровень и XP выше его границы нельзя.

Интерфейс принимает готовые границы. Он не угадывает следующий порог по номеру уровня. Неизвестный порог, неверная версия или нулевой диапазон показывают unavailable; если продукт когда-нибудь введёт максимальный уровень, он передаётся явным `max_level`, а не определяется числом 999.

### Демонстрационные границы

Для проверки макетов подготовлен генератор фикстур, совпадающий с профилем выше. Это не предложение утвердить награды или темп роста:

```text
R(1) = 250
R(L) = 250 × L + 250, если 2 ≤ L ≤ 11
R(L) = 3 500 + 250 × (L − 12), если L ≥ 12
T(1) = 0
T(L) = сумма R(k) для k от 1 до L−1
```

Здесь `R` — XP на следующий уровень, `T` — накопленный порог начала уровня. Для L ≥ 12, n = L − 12: `T(L) = 19 000 + 3 500n + 125n(n−1)`. Проверены уровни 1, 10, 12, 27, 100, 999, 1 000 и 1 000 000 000. Огромные значения проверяют числовую устойчивость, а не предполагаемую длину игры.

XP и уровни в stress fixtures записаны десятичными строками. После превышения `Number.MAX_SAFE_INTEGER` нельзя преобразовывать lifetime XP в JavaScript Number до вычитания границ: потеряется точность. Использовать серверные integer/decimal либо BigInt для целых значений. Для доли достаточно вычислить отношение точных числителя и знаменателя до ограниченной точности визуала; значение для подписи хранить отдельно. Потеря менее пикселя при отображении не должна изменять учёт XP.

Форматирование: `2 840`, `21 840`, `1 000 000` по русской локали. Для больших значений в тесной карточке допустимо `1,2 млн XP` с полной строкой в раскрытии/tooltip; никогда не подставлять сокращённое число обратно в вычисление. Номер уровня не обрезать до «999+» там, где пользователь открыл профиль для точного просмотра; `999+` возможен лишь как компактный бейдж с полным доступным текстом.

## 5. Награда, повторное событие, возврат и reconnect

Клиент не начисляет XP из факта показа success modal. Источник истины — подтверждённый серверный ledger и его revision.

Награда должна иметь стабильный `grantEventId`, пользователя, тип и ID источника, сумму, время и состояние. Идемпотентный ключ для достижения — пользователь + стабильный achievement ID + период, если определение повторяемое. `definitionVersion` хранится для аудита; одно изменение описания не должно повторно выдавать награду. Для ступеней серии используются отдельные стабильные achievement IDs. Награда за задачу привязана к первому подтверждённому accepted результата задачи, а не к каждой отправке кода.

| Событие | Как изменяется интерфейс |
|---|---|
| Решение отправлено | Pending; можно показать будущую награду, но общий XP остаётся подтверждённым |
| Сервер подтвердил +25 / +120 XP | Обновить authoritative snapshot; один компактный `XP/Reward` |
| То же событие пришло повторно | Нулевое повторное начисление; не повторять анимацию |
| Один результат дал несколько наград | Применить согласованный snapshot и показать одну сводку с деталями источников |
| Переподключение | Сохранить последний подтверждённый XP, показать «Обновляем прогресс»; получить новый snapshot/revision |
| Старый ответ пришёл после нового | Не заменять новый revision старым |
| Между визитами получено несколько уровней | Одна сводка «Уровень 12 → 15» и итоговый XP; не запускать очередь старых modal |
| Возврат оплаты курса | Меняется доступ к курсу; исторический прогресс и XP не списываются автоматически |
| Подтверждённая ошибка выдачи/исправленный verdict | Отдельное компенсационное событие с reference на grant, одна корректировка и понятное пояснение |

Компенсация не удаляет ledger entry: у неё собственный уникальный ID и ссылка на исходную награду. Повторная компенсация того же grant не должна дважды вычесть XP. Если пересчёт опускает пользователя ниже границы, сервер присылает согласованные уровень и значения. Клиент не показывает праздничный Level Up при понижении. Неизвестная причина не превращается в обвинительный текст.

`lifetimeXp` в UI — подтверждённая сумма XP за всё время с применёнными корректировками, не баланс для оплаты и не валовой счётчик без отмен. При необходимости ledger отдельно хранит gross earned и reversals. Некорректный отрицательный итог — ошибка данных, а не основание молча скрыть её clamp до нуля.

Для достижений «10 000 XP» / «100 000 XP» метрика примера `xp.eligibleLearningEarned` учитывает подтверждённые учебные награды и их корректировки, **исключая бонусы самих достижений**. Это предотвращает самоподдерживающуюся выдачу. Если продукт выберет другую политику, она должна быть явной и версионированной.

Потеря связи не стирает введённый код или заметки. После reconnect результат submission и прогресс перечитываются; создание нового submission ради восстановления экрана не требуется. Анимация награды использует подтверждённые ещё не показанные IDs; после refresh не проигрывает старые награды заново.

## 6. Компоненты XP

| Компонент | Свойства | Дискретные состояния |
|---|---|---|
| `Progress/XP` | level, currentLevelXp, requiredXp, remainingXp, showNumbers, size | determinate, indeterminate, unavailable, max-level при явной политике |
| `Level/Badge` | level, size, compact, fullAccessibleLabel | default, highlighted; номер уровня не variant |
| `XP/Reward` | amount, sourceLabel, grantEventId | pending, confirmed, reversed; duplicate не создаёт второй UI |
| `LevelUp/Modal` | previousLevel, newLevel, crossedLevels, currentXp, requiredXp | single-level, multiple-level, dismissed |
| `XP/Summary` | lifetimeXp, periodXp, sources, revision | ready, loading, reconnecting, error, corrected |

Подписи простые: «+25 XP», «+120 XP», «Уровень 13», «До следующего уровня 660 XP», «Результат сохранён», «XP пересчитан после изменения результата». Без мотивационных лозунгов.

Level Up пример: уровень 12, 3 400 / 3 500 XP; награда +120. Было всего 22 400, стало 22 520. Итог: уровень 13, **20 / 3 750 XP**, осталось **3 730 XP**. Эти числа находятся в JSON и проверяются арифметически.

## 7. Определение достижения и состояние пользователя

Для production разумно разделить definition и user progress. В локальном JSON они объединены, чтобы удобно заполнять макеты. `id` стабилен при изменении названия, категории, иконки или перевода. Порядок массива не является ID.

Definition: `id`, `title`, `description`, `icon`, `category`, `xpReward`, `rarity`, `metricKey`, `metricScope`, `target`, `secret`, `tier`, `definitionVersion`.

User progress: `current`, `percentage`, `state`, `unlockedAt`, `isNewlyUnlocked`, `progressVersion`. Unlock event приходит сервером. Клиент не получает доступ к награде просто потому, что нарисовал 100%.

Рекомендуемый target — положительный целый счётчик. Для дробной доменной метрики сохраняется тип/единица измерения. Счётчики из разных metricScope не смешиваются: «Пройден вводный модуль Java» не равно «Пройден любой модуль».

`rarity` — отдельная характеристика: common / uncommon / rare / legendary. Категория и редкость не определяют факт получения. Новая редкость получает нейтральное оформление по умолчанию, пока не добавлен token; UI не должен ломать карточку.

### Девять категорий

| Стабильный ключ | Подпись | Совместимость со старым каталогом |
|---|---|---|
| Learning | Обучение | Теория |
| Coding | Задачи | Практика |
| Courses | Курсы | Курсы |
| Incidents | Инциденты | Новая категория |
| Reviews | Проверка кода | Новая категория; не путать с повторением темы |
| Streak | Регулярность | Регулярность |
| XP | Опыт | Новая категория |
| Special | Особые | «Разные темы» как пример межтематического достижения |
| Hidden | Скрытые | «Послойная практика» как локальный пример секретного определения |

Legacy category default map находится в JSON. Overrides перечислены явно, а не выводятся из переведённого текста. Возвращение к теме и review due — учебное повторение; Code Review — анализ чужого кода. Для них разные metricKey и разные UI названия.

Восемь дополнительных записей: «Первое ревью», «Первый инцидент», «Пятьдесят инцидентов», «10 000 XP», «100 000 XP», «Основы Java», «Курс Java завершён», «Десять исправлений». Названия не дублируются. Старые 30 SVG сохраняются, их связь со стабильным achievement ID задаётся данными.

## 8. Achievement components и состояния

| Компонент | Что меняется через properties |
|---|---|
| `Achievement/Icon` | instance swap существующего символа, size 32/64/128, tone |
| `Achievement/Card` | icon, title, description, category, XP, rarity, current/target, date, state, tier |
| `Achievement/Grid` | коллекция cards, число колонок от контейнера, pagination/loading/empty |
| `Achievement/Progress` | current/target, непрерывное заполнение, compact/full |
| `Achievement/Locked` | описание условия и отсутствие unlock date; не «нет доступа к странице» |
| `Achievement/Unlocked` | дата получения и подтверждённая награда |
| `Achievement/Secret` | только разрешённая анонимная проекция, без скрытого условия |

Это связанные compositions/variants одной системы, а не семь независимых реализаций карточки. `newly unlocked` — краткое состояние презентации unlocked + `isNewlyUnlocked`; `completed` — синоним полученного достижения, не ещё один несовместимый enum. Rare/legendary — rarity property, не state вместо locked/progress.

В locked используется приглушённая геометрия, но текст условия остаётся читаемым. В progress видны точные количества: **72 / 100**, а шкала занимает 72%. В unlocked — явный статус «Получено» и дата. Для secret видна подпись «Скрытое достижение» и «Подробности появятся после получения».

Карточка не имеет фиксированного ограничения на две строки переведённого названия. Краткое описание допускает несколько строк. Если коллекция использует одинаковую высоту, раскрытие показывает полный текст; title не исчезает без доступного способа прочитать его целиком.

Значки остаются в 128×128 master bounds. Для маленького применения использовать 32/64/128 отображение и обычный Scale в будущем Figma; не переписывать path для каждой награды. При совпадающем glyph разных tier различие передаётся названием/номерной меткой, а не только цветом.

## 9. Сотни и тысячи достижений

Коллекция грузится порциями. Рекомендуемый пример — 24 записи; 1 000 элементов дают 42 страницы, последняя содержит 16 записей. Размер страницы — настройка запроса, не ограничение компонента. Для меняющейся коллекции предпочтительна cursor pagination с стабильным tie-breaker по ID.

Фильтры: Все / Получено / Не получено / В процессе, категории, при необходимости поиск по доступным названиям. `Не получено` включает нулевые и частичные публичные определения; `В процессе` — только публичные с current > 0 и без unlock. Secret не вычисляется клиентом по проценту.

Сортировка: Недавно получено / Прогресс / Редкость. Для Недавно получено первичен unlock timestamp; null располагается после полученных. Для Прогресс используется точное отношение, затем стабильный ID; одинаковые округлённые подписи не должны вызывать случайные перестановки. Редкость использует явный rank, не алфавит переведённых слов. При смене фильтров cursor сбрасывается, старый запрос отменяется или игнорируется по request ID.

Сервер возвращает `items`, `nextCursor`, `hasMore`, согласованный `snapshotRevision`; total count нужен только если разрешён политикой видимости. Тотал и фильтры считаются сервером по той же доступной проекции, а не по всем скрытым определениям. Load more сохраняет позицию и focus; explicit pagination переносит focus к заголовку результата. Изменение query/state хранится в URL там, где это уместно для навигации назад.

Не рендерить 1 000 сложных SVG сразу. Порционная загрузка и lazy previews достаточны для начала; virtualized grid можно добавить для длинной уже загруженной коллекции, сохранив keyboard order и высоты строк. На mobile карточки идут одной колонкой, фильтры — в drawer; менять ширину самого SVG для создания «новой иконки» не требуется.

Состояния коллекции: initial loading, skeleton, populated, loading more, exhausted, no earned achievements, empty filtered result, network error, offline snapshot, reconnecting. Ошибка следующей страницы не удаляет уже видимые карточки: рядом с Load more появляется «Не удалось загрузить ещё. Повторить».

## 10. Секретность и доступ

Полный secret record в локальном файле нужен автору spec. Его нельзя напрямую включать в публичный frontend bundle. Он содержит истинное условие, метрику и награду. Production API отдаёт отдельную projection до unlock:

```text
opaque public ID
generic hidden icon
«Скрытое достижение»
«Подробности появятся после получения»
state = secret
reward/current/target/percentage/date = null
```

До раскрытия не отправлять metricKey, scope, target, настоящий title/description/icon, tier family и условие раскрытия. Не хранить их в скрытом DOM, alt, tooltip, data attributes, analytics payload или поисковом индексе клиента. Семантический ID вида `solve-50-incidents` тоже раскрывает условие: использовать непрозрачный public slot ID.

Если даже количество секретных определений не должно быть известно, не возвращать placeholder для каждого и не включать их число в total. Политика видимости проверяется на сервере для пользователя и запроса; category filter, сортировка и детализация не обходят её. Ошибки доступа 403 не заменяются «у вас нет достижений».

После подтверждённого unlock сервер отдаёт раскрытый record. Карточка меняется один раз; screen reader получает краткое событие «Получено достижение: …». Содержимое не раскрывается из одного клиентского локального счётчика.

## 11. Learning states, Spiral и Review Due

`accessState`, `learningState`, `reviewState` и `isCurrent` независимы:

- Access: available / preview / locked / revoked. Покупка и prerequisite — причины locked, а не нулевого процента.
- Learning: not_started / in_progress / completed. Для задачи добавляется отдельный verdict, для review/incident — собственный рабочий lifecycle.
- Review: none / due_soon / due / overdue / refreshed.
- Current: выбранный или рекомендуемый следующий элемент; completed урок тоже может быть открыт сейчас.

У Module/Card есть number/title/description/count/duration/progress и expanded. У Lesson/Row — type icon/title/duration/XP/progress/status/last activity. Типы: THEORY, TASK, QUIZ, TRANSFER, CODE REVIEW, INCIDENT, PROJECT. Новый type получает generic activity icon и переданный title; frontend не должен падать из-за неизвестного enum.

Для `SkillProgress/Spiral` три смысловых ступени:

| Stage | Что подтверждается | Пример HashMap |
|---|---|---|
| UNDERSTAND / Разобраться | Понимание механики и базового примера | completed |
| APPLY / Применить | Самостоятельное применение в практических условиях | 18 / 25 = 72%, current |
| MASTER / Освоить глубже | Перенос, границы, анализ и работа с усложнениями | locked до выполнения prerequisite |

Каждый `SkillStage` поддерживает locked/available/current/completed, title, evidence progress и действие. Ступень не называется «урок в третий раз». Гейт Master определяется явными результатами, а не только длительностью присутствия. `SkillMasteryBadge` принимает отдельную оценку mastery и confidence/unknown при необходимости; среднее процентов трёх стадий не считается освоением автоматически.

Review Due — предложение освежить практику. Пример: HashMap, mastery **84%**, последняя практика **42 дня назад**, кнопка **«Повторить»**. В фикстуре 29 июля → 9 сентября 2026 ровно 42 дня. Это отдельный более поздний снимок, не противоречивое дополнение к текущему APPLY 72%.

Review states имеют ясные подписи: due soon — «Скоро повторить», due — «Пора повторить», overdue — «Повторение отложено», refreshed — «Повторено». Просрочка не окрашивает пользователя как провалившего курс, не забирает исторический completion и не списывает XP. Она может сосуществовать с completed. Время вычисляется из timestamp/dueAt по согласованным server clock и часовому поясу, а не из захардкоженной строки «42 дня».

После практики обновляются lastPracticedAt, reviewState и модель mastery из одного согласованного ответа. Отмена старого due reminder не создаёт новое XP событие. Loading/error/reconnecting review-компонента сохраняют прошлые подтверждённые значения и поясняют актуальность.

## 12. Проверки готовности данных и переноса

- Все исходные 30 названий и SVG сохранены; 38 ID и названий уникальны.
- Все девять enum категорий представлены; legacy mapping и два overrides явные.
- Каждый icon path существует; дополнительных raster или новых SVG нет.
- current ≥ 0, target > 0, percentage соответствует current / target с ограничением 100.
- unlocked требует date и подтверждённое состояние; locked/progress/secret не имеют unlock date.
- Secret projection не раскрывает критерий и точный счётчик.
- Профиль: 21 840 − 19 000 = 2 840; 22 500 − 21 840 = 660.
- Курс: сумма модулей 43 / 60; HashMap 65% не прибавляет завершённый урок.
- Уровни 1 / 10 / 100 / 999 / 1 000 и огромный stress value не переполняют точные расчёты.
- Exact level boundary, zero denominator, unknown, negative input, count above target и rounding near 100 разобраны отдельно.
- Повторное событие, compensation и reconnect не дублируют награду или modal.
- Никакого percentage variant на каждое значение; свойства данных и состояния разделены.
- При переносе в Figma повторяемые карточки/стадии — Components и instances; dataset только заполняет их свойства. На текущем этапе это локальная спецификация, не созданные в Figma экраны.
